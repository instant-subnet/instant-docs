Validator guide

Keep burn live. Score miners in shadow. Cut over once.

An Instant validator is a small PM2-managed service. During launch testing, its production writer keeps 100% burn on-chain while the report path computes and logs the exact prospective UID weight vector without submitting it.

The launch validator is still being implemented

Burn remains enabled through every implementation and testing phase. Phase 4 makes the report and scoring path production-ready, but scoring vectors stay in logs. Burn is disabled only after every phase passes, a real miner is onboarded and accepted, and the final go-live cutover is explicitly approved.

Prerequisites

  • A Linux host with reliable time, storage, and outbound HTTPS/Finney access.
  • An operational validator hotkey registered on Finney subnet 46 with the required permit and stake.
  • The reviewed Instant validator release and its pinned dependencies.
  • The expected platform report URL and signer identity.
  • A private .env containing wallet and service configuration.

Use an operational hotkey only

The validator host does not need the owner's mnemonic, seed phrase, or private coldkey.

One supervised process

Configure once and let PM2 run the loop

  1. Create private configuration

    cp .env.example .env

    Set the validator wallet, platform report URL, schedule, Finney, and netuid 46.

  2. Start the service

    pm2 start ecosystem.config.cjs

    PM2 supervises one non-interactive validator process.

  3. Inspect bounded status

    pm2 status instant-validator

    Confirm the service is online and not restarting before inspecting its bounded log tail.

  4. Keep scoring in shadow

    Review each logged report ID and UID/weight vector while the production burn writer remains active.

Both paths are fail-closed. Before go-live, only the 100% burn vector may be submitted. After the one approved cutover, the deterministic scoring vector becomes the direct set_weights input. Commit/reveal and interactive one-shot commands are outside MVP.

Burn plus shadow scoring

The platform supplies the miner rows

  1. Wait until the configured weight time.
  2. Fetch the latest completed report from the platform.
  3. Verify its signature, schema, network, netuid, freshness, and report ID.
  4. Score the supplied UID rows with one deterministic formula and normalize weights.
  5. Log the report ID and exact prospective UID/weight vector, then wait again.

The platform verifies miner registration and publishes both UID and hotkey. Validators trust that roster in MVP; optional independent reconciliation can be added later as a preflight.

Final go-live is a separate operation

Only after every phase passes and an onboarded miner is accepted does an operator disable burn and allow the reviewed scoring vector to reach set_weights. That cutover is never part of a Phase 4 test.

Current limitations

  • The validator trusts the platform's signed miner roster and metrics in MVP.
  • It does not query or probe miners directly.
  • Invalid, stale, duplicate, wrongly signed, wrong-network, or empty reports never reach the scoring writer.
  • There is one scoring formula and one direct writer path.
  • Phase 4 logs scoring vectors but does not replace the active burn vector.
  • Disabling burn and enabling the first scoring write requires explicit final go-live approval.
