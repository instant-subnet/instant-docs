Validator guide

Set up and operate an Instant Validator.

Install the small Validator service, keep its updater and scheduled run healthy, and inspect per-Miner scoring logs from one Linux host.

Quick start

Install the Validator

git clone https://github.com/instant-subnet/instant-subnet.git
cd instant-subnet
cp .env.example .env

Open .env and set these values before starting: 

INSTANT_NETWORK=<network>
INSTANT_NETUID=<netuid>
INSTANT_PLATFORM_REPORT_URL=https://api.instantsubnet.com/validator/v1/reports/latest
INSTANT_PLATFORM_SIGNER=5E1oV49jn5s2pZMkn1NSNCE3pU6afjKMcAhDPvy2iZacQVp5
INSTANT_WALLET_NAME=<wallet name>
INSTANT_WALLET_HOTKEY=<hotkey name>
INSTANT_WALLET_PATH=~/.bittensor/wallets

The network and netuid must match the subnet where the Validator is registered. The Platform signer must match the signer published for that network; do not accept a replacement signer from an untrusted report. The wallet path must contain the named operational hotkey.

Start the Validator with:

python3 scripts/start_validator.py

The setup prepares the environment, installs the scheduled Validator run, starts the PM2 updater, and saves the PM2 process list.

If PM2 startup is not already configured on the host, run pm2 startup once and execute the command it prints.

Prerequisites

  • A Linux host with Python 3.11+, Git, cron, flock, Node.js, and PM2.
  • Reliable time, storage, outbound HTTPS, and access to the configured chain network.
  • An operational Validator hotkey registered on the target subnet with the required permit and stake.
  • The expected Platform report URL and exact report signer SS58 address.
  • A private .env containing the network identity and wallet location.

Use an operational hotkey only

The validator host does not need the owner's mnemonic, seed phrase, or private coldkey.

Daily operation

Keep PM2 and cron healthy

pm2 status instant-validator-updater
crontab -l | grep instant-validator-run-once
tail -n 100 logs/validator.log

The updater should be online in PM2, the Validator cron entry should be present, and the scoring log should show completed scheduled runs. The updater and Validator each wake every five minutes. A shared lock prevents an update and a Validator run from changing the checkout at the same time.

Run the Validator once and inspect its live log with: 

scripts/run_validator.sh
tail -f logs/validator.log

A healthy scheduled run either logs a newly scored report or records that there is no new work. Repeated failures belong in the Validator troubleshooting guide.

Deterministic integer math

Speed leads the score

The Validator receives signed aggregate metrics for each Miner: UID, hotkey, request counts, verified completion tokens, generation speed, and proof outcomes. Customer prompts and responses are not included. Only proof-verified successful work contributes positive speed and token metrics. Each relative component compares the Miner to the best eligible Miner in that report: 

component_bps = floor(miner_value × 10,000 / report_max_value)

score_bps = floor(
    (60 × speed_bps
   + 25 × tokens_bps
   + 10 × requests_bps
   +  5 × success_bps) / 100
)

normalized_weight = floor(score_bps × 65,535 / highest_score_bps)

A zero report maximum produces a zero component. Success rate is floor(successful_requests × 10,000 / routed_requests). Any failed or timed-out proof makes that Miner's whole report-epoch score zero, while remaining proofs continue to run and appear in the report. A verified finish_reason=length is successful and all completion tokens count.

The scoring log contains one record per Miner with report ID, UID, hotkey, raw metrics, component scores, final score, and normalized weight.

Platform routing

Ninety percent performance, ten percent discovery

The Platform applies smooth weighted scheduling for nine requests, then one equal-discovery request across currently eligible Miners. Before the first report, or when all report weights are zero, routing is equal. New Miners therefore receive discovery traffic and enter the next scoring cycle.

Busy, disconnected, held, or unready Miners are skipped even if a report contains a positive weight. The Validator does not connect to or probe Miner hosts; it consumes the Platform's signed aggregate.

Maintenance

Update or restore the schedules

Run the same updater manually when you do not want to wait for PM2:

python3 scripts/update_validator.py --once

After host maintenance, rerun python3 scripts/start_validator.py to restore the PM2 updater and cron entry. Accepted report state is kept on disk, so a service restart does not score the same report again. Do not delete the Validator state directory during an update or restart.

Current limitations

  • Scoring relies on the Platform's signed Miner roster and aggregate metrics.
  • The Validator does not query Miner hosts or inspect customer prompts and responses.
  • Invalid signatures, network settings, report data, or UID/hotkey mappings stop that run.
  • A report with no Miner work is valid and produces no Miner scores.
  • The current release supports one scoring formula and one scheduled workflow.
